多 Agent 开发流程编排平台

让多个 Agent 像一支公司一样
自动流转，而不是互相聊天

一个需求输入，多个角色自动走完「立项 → 需求 → 设计 → 编码 → 测试 → 评审 → 集成 → 发布 → 验收」。 角色之间零自由对话，只交换结构化产物；所有状态变更都是追加事件， 任务的当前状态是事件重放的投影 —— 任何时刻都能回答「为什么走到了这一步」。

它解决什么问题

根因判断：把 agent 当「人」来协调。人类协作靠对话和默契， agent 协作必须靠结构化契约 + 显式状态机 + 唯一状态真相。

01

无唯一事实来源

每个角色只知道自己手上的事，没人持有全局状态，判断「下一步该谁做」只能靠人。

02

无交接契约

上游产出以自然语言散落，下游需要什么、产出什么格式全靠默契，导致反复返工。

03

无终止条件

一旦允许角色自由对话，容易陷入互相追问的死循环，且成本不可控。

04

不可观测

任务卡住时，无法回答「卡在谁身上、为什么卡、已消耗多少」。

05

并行是假象

想靠「多开几个 agent」提速，结果是多个实例改同一批文件，冲突与覆盖在跑完才发现。 并行必须由工作包拆解自然决定，而不是调度器硬凑。

06

成本与风险失控

让最强模型全程参与，一个需求会烧掉几十倍 token；高风险动作（上线发布、预算超限） 缺少「必须真人批准」的硬卡点。

三条决定性设计原则

这三条贯穿全文，是后续所有设计取舍的判据。

唯一状态真相在内核，不在 agent

所有状态变更都是追加事件（append-only event）。任务的「当前状态」是事件重放的 投影，不是某个 agent 的记忆。

→ 可回溯、可重放、可精确复现「为什么走到这一步」。

角色间零自由对话，只交换结构化产物

每个角色声明 inputs: Artifact[] 与 outputs: Artifact[]。 产物落库后由状态机判定下一跳。

→ 责任链清晰，不靠 agent 自觉；成本可控；不会陷入互相追问的死循环。

大内容不进 prompt，只进引用

Artifact 的 summary（≤500 token）进下游 prompt，正文只以 refs 引用， 需要细节时 agent 自己去工作区读。

→ 解决上下文爆炸与信息丢失，这是多 agent 协作里最容易踩的坑。

核心机制

六件事，构成「可自动流转」的最小完整集合。

事件存储是唯一状态真相

事件表只追加、不修改。投影表（task_state / node_state）可从 events 完整重建，随时可丢弃。每条转移都记录 reason 与 decided_by（rule / llm / human）。

结构化产物，零自由对话

信息只走三条通道：① Artifact 事件总线（唯一决定流程走向）；② git 工作区； ③ 受限问答（单轮、只读工具、token 上限极小，回答也必须以 Artifact 落库）。

工作包并行

并行度来自需求阶段的工作包拆解，而不是调度器硬凑。工作包声明 owns（拥有的路径）/ reads / depends_on / interface_contract（冻结后不可变）。

G0–G3 卡点

  • G0 规则自动通过，无角色介入
  • G1 单角色审批（代码评审）
  • G2 多角色会签（架构冻结、合并、验收）
  • G3 真人审批，流程挂起等待

CEO 全程只出现在 4 个 G3 节点，不参与任何中间环节。

三档 profile

  • full — 全部 12 角色，评审 2 人，CEO 全部 4 个 G3
  • lean — 去掉 ux_designer，评审 1 人，G3 仅保留上线发布
  • solo — 仅 dev + qa + 1 评审，无 G3

profile 是角色集的过滤视图 + gate 级别覆写，不改流程拓扑。

可观测

观测前端提供：任务总览、DAG 泳道图、实时日志、人工卡点队列、组织视图、成本面板、产物浏览器。 原始日志不进事件库，只存 log_ref 引用，事件库保持小而快。

刻意不做的事（非目标）

分布式多机调度 · 自研 LLM 工具调用循环（复用 claude / codex CLI）· 通用工作流引擎（转移条件用受限表达式，不做图灵完备脚本）· 图形化流程编辑器（流程用 YAML， 页面只做观测）· 多方案并行择优（成本翻倍，列为远期可选项）· 多人协同与账号体系（单用户本地平台， 仅绑定 127.0.0.1）。

存储

事件真源 + 投影 + 日志文件

关键约束：事件只追加，不修改。

SQLite：events（真源）· projections · logs/（引用）。 另含 tasks / work_packages / node_runs / artifacts / gates / leases 数据表。

Runner Pool

把角色翻译成 CLI 调用，采集产出

关键约束：引擎无关的归一化事件流。

claude-code adapter（Phase 1 已实现）· codex adapter（Phase 3）· git worktree 池（Phase 2）。内核不认识 CLI，只消费 RunnerEvent。

能力不对称是真问题

claude 有 --json-schema 与 --max-budget-usd， codex 都没有。因此 capabilities（structuredOutput / budgetCap / sessionResume / builtinReview）是 Runner 接口的一等成员，内核按能力降级：无结构化输出则用 prompt 强约束 + JSON 提取容错 + zod 校验失败即重试一次；无预算上限则由内核记账层兜底、超限主动 cancel。

Phase 1 的实现边界（如实说明）

  • 串行：内核单节点推进，AGENTFLOW_GLOBAL_CONCURRENCY 目前无消费者。
  • 无路径级强制：owns 仅作为 prompt 提示；内核层无变更路径核对， artifact.invalidated 在 Phase 1 无生产者，不得当作安全边界。
  • 无 worktree 隔离：Phase 1 所有节点 isolate: false（无合并能力， 在 worktree 里写代码会在回收后丢失）。
  • 可写角色的命令白名单已实质放宽：Bash(sh:*) / Bash(bash:*) 等价于任意命令执行，收窄属 Phase 2 决策。
  • 路径级强制、占用检查、worktree 合并、G1–G3 卡点、codex 适配器均为 Phase 2+。

角色组织

核心机制是角色模板 + 实例池：不是预定义 dev_1..dev_5， 而是一个角色模板按工作包数量动态 spawn 并发实例。3 个工作包 → 3 个并发实例， 并发度由工作包数量自然决定，无需手工维护个体。角色定义是声明式 YAML，不是代码。

交叉引擎评审

规则：评审员使用的引擎必须与产出该代码的实例所用引擎不同，由内核在调度评审节点时动态分配。 同一引擎自评有同源盲区（倾向认为自己的写法对），这是「独立 QA」概念的真实价值； 两个 reviewer 之间的引擎也必须不同，否则等于同一视角评两遍。

一条值得记住的工程细节：产物格式下沉到 CLI 层强制

所有 Artifact payload 用 zod 定义并导出 JSON Schema，这份 schema 直接作为 claude --json-schema 的参数 —— 把产物格式下沉到 CLI 层强制， 而不是「求 agent 按格式输出」。内核再用 parseArtifactPayload 把模型给出的 status 提升为 Artifact 的独立列并消费，工作流边条件（如 all(artifacts.requirement.status == 'ok')）因此真正生效。

Phase 0–5 路线图

每个阶段都是能跑起来的闭环，不是半成品。进度如实标注：Phase 0/1 已完成， Phase 2 及之后规划中。

  1. Phase 0 已完成

    CLI 行为探针

    Runner 适配层的实现完全取决于 CLI 的真实输出行为，不能靠推测写，因此本阶段阻塞后续、必须最先做。 验证 claude -p --output-format stream-json 的真实事件序列、--json-schema 在有工具调用时的可靠性、codex exec 的可解析性、多实例并发安全性、--max-budget-usd 行为。

    产出：spikes/cli-probe/ 最小脚本 + 结论写回 记录.md；真实成功样本归档为 fixture。

  2. Phase 1 已完成

    内核骨架（单引擎串行闭环）

    EventStore + Projector + StateMachine（规则求值）、 RunnerPool + claude-code adapter、三个角色 pm → backend_dev → qa_engineer、极简页面（任务列表 + 状态流转）。

    验收：输入一个需求文本，三个角色自动串行流转完成，事件库能重放出完整过程。

  3. Phase 2 规划中

    并行

    工作包拆解（work_package_plan）+ owns 占用检查、 parallel / join 节点类型、WorkspaceManager + worktree 池、 integrator 角色 + conflict_report、路径级强制与越界检出。

    验收：一个需求拆出 3 个工作包，3 条泳道并行跑，自动合并。

  4. Phase 3 规划中

    完整公司与卡点

    全部 12 角色注册表 + 三档 profile、G1 / G2 / G3 卡点 + GateKeeper、 codex adapter + 交叉引擎评审（codex review --base）、人工卡点队列页面。

    验收：full profile 跑通完整流程，CEO 只在 4 个 G3 出现。

  5. Phase 4 规划中

    观测前端完整版

    DAG 泳道图 + 实时日志流 + 组织视图 + 成本面板 + 产物浏览器。

    验收：不读日志文件，仅从页面就能回答「现在谁在干什么、卡在哪、为什么、花了多少钱」。

  6. Phase 5 规划中

    鲁棒性

    Lease / 心跳、幂等重试、反死锁、预算准入、事件重放重建投影、LLM 决策器（受限枚举）。

    验收：强杀进程后任务能被正确判定失败并重试；预算超限正确挂起。

快速开始

单机本地运行，HTTP / WebSocket 仅绑定 127.0.0.1，无鉴权需求。

1. 准备环境

需要 Node 22+，并已安装并登录 claude CLI（Phase 1 单引擎依赖它）。

node --version   # 需 >= 22
claude --version # 需已登录

2. 安装依赖并配置

npm install
cp .env.example .env   # 按需修改，.env 不提交

所有可变配置走 .env（模板 .env.example），代码内只通过 src/config/env.ts 读取；禁止硬编码路径与密钥。

3. 启动

npm run dev    # tsx watch src/main.ts
# 或
npm start      # tsx src/main.ts

启动后终端会打印 AgentFlow 已启动：http://127.0.0.1:8787。

4. 质量门

npm test        # vitest run
npm run typecheck  # tsc --noEmit

端到端闭环长什么样

输入一个需求文本 → pm 产出 requirement 与 work_package_plan → backend_dev 产出 code_diff → qa_engineer 产出 test_report → 状态机按边条件判定下一跳， 全程事件可重放。Phase 1 实现的 Artifact 类型只有 4 种： requirement / work_package_plan / code_diff / test_report。
