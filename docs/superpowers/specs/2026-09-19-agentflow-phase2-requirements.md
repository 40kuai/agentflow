## 1. 需求依据：Phase 1 的实测边界

Phase 1 已交付并跑通端到端（一个需求 → PM/后端开发/测试 三角色串行 → `completed`，3/3 artifact）。以下每一条都是**实测或代码核实**的边界，构成 Phase 2 的需求来源。

### 1.1 安全边界（最优先）

| # | 实测事实 | 后果 |
| --- | --- | --- |
| S1 | 内核 `repoPath` 取 `process.cwd()`；平台**没有"目标仓库"概念** | 把平台指向自身源码树时，agent **改写了平台自己的仓库**：仓库根出现 `README.md`、`scripts/hello.sh`、`tests/hello-script.test.ts`，并**导致 `tsc` 失败**（该测试文件不受编译约束）。这不只是"越界写"，而是**平台可自污染** |
| S2 | `owns` **无路径级强制**：`backend_dev.yaml` 声明 `owns: ["src/**"]`，agent 实际写了 `README.md` 与 `scripts/hello.sh`，任务仍正常 `completed`；`artifact.invalidated` 事件**全仓无生产者** | spec §7.2/§15 称它为"硬约束"，实际只是 prompt 里的一句话 → 文档与实现不符，**不可被当作安全边界** |
| S3 | headless 下 `--permission-mode acceptEdits` **不放行命令执行**（实测同一任务 461 次 `This command requires approval`），改预授权后降到 7 次 | 权限模型必须与角色契约一起设计；否则角色无法履行其产物 schema 的要求（如 `self_test_result`） |
| S4 | 预授权是**前缀白名单**，但 `Bash(sh:*)`/`Bash(bash:*)` **等价于任意命令执行**（`bash -c "…"`、`curl … \| sh` 绕过前缀）；`Bash(git:*)`/`Bash(npm:*)` 含 `push --force`/`reset --hard`/`publish` | "精准预授权"在能力层面退化为全量放行；需在 Phase 2 收窄或改为显式命令清单 |
| S5 | `--tools` **不约束 MCP 工具** | 只读角色的"只读"在 CLI 层并非 airtight |
| S6 | `--max-budget-usd` 只在"有预算上限"时才传，而内核**从不传** `budgetCapUsd` | **单节点花费无上限**；且降级重试使 wall-clock 与预算上限实际为标称值的 **2×** |
| S7 | 实测到一个 `claude` 进程**存活 6 小时 24 分**未清理 | 孤儿进程需要可观测 + 可清理，不能只靠退出钩子 |

### 1.2 并行能力（用户明确关注）

| # | 实测事实 | 后果 |
| --- | --- | --- |
| P1 | 内核 `runNode` 是**单节点 `await`**，一次只跑一个节点 | **并发协作不存在**。spec §1.2 的"尽可能并行"未实现 |
| P2 | `AGENTFLOW_GLOBAL_CONCURRENCY=4` 被 `env.ts` 解析，**全仓无消费者** | 配置假象：看上去支持并发，实际无效 |
| P3 | `parallel`/`join` 节点类型**零实现**（全仓检索无命中） | 工作流只能是链式 |
| P4 | `work_package_plan` 的 payload schema **已定义**（含 `interface_contract`），但 `simple_dev.yaml` **没有节点产出它** | 并行度的来源（spec §10.1：PM 工作包拆解）尚未接入 |
| P5 | worktree 隔离**有骨架不可达**（`isolate` 全为 `false`） | 无合并能力时隔离会丢代码 → 这是"先串行跑通闭环"的合理取舍，但 Phase 2 必须解开 |
| P6 | 前端曾显示**恒为 0 的"并行度"**指标 | 假指标比不显示更糟（已改为如实标注） |

### 1.3 可观测性与生命周期

| # | 实测事实 | 后果 |
| --- | --- | --- |
| O1 | `{type:'event'}` 推送**无触发点**（内核无事件订阅接口），Phase 1 前端靠 2 秒轮询 | 节点级实时性缺失；长任务的"是否在推进"依赖轮询+日志 mtime 这类间接信号 |
| O2 | **缺少取消/暂停能力**：库里存在永远 `active` 的僵尸任务（`task_e5cb8206`），导致启停脚本的安全护栏每次都被触发 | 无任务生命周期管理，运维护栏失去判别力 |
| O3 | `GET /api/tasks` 每次全量 `readAll()` + `project()` | 事件量大后需索引/分页 |
| O4 | 前端 WS **无重连**，任务列表只在挂载/WS 消息/创建后刷新 | WS 断后列表永久停在旧值 |
| O5 | 事件里 `node.usage_recorded` 与 `budget.consumed` **双写同一笔钱**（投影器只累计前者，当前不重复计费） | 同源冗余事件是后续消费者（成本闸门）的坑 |
| O6 | `ArtifactSchema` / `ARTIFACT_SCHEMA_VERSION` **无任何运行期消费者**；`schema_version` 被硬编码为 `1` | schema 声明与实际校验脱节 |

### 1.4 契约缺陷（已修但留下教训）

| # | 事实 | Phase 2 要求 |
| --- | --- | --- |
| C1 | Artifact `status` 曾在契约中缺失，模型只能把 `blocked` 判断塞进 `problem` 散文，而工作流边条件依赖 `status` → **模型语义判断被静默吃掉** | 契约与消费方必须同时改；新增字段必须有真实消费者，否则视同未实现 |

| C3 | 实测任务因 `error_max_structured_output_retries` 零产出（22 轮 / 103 秒 / $0.417） | 结构化产出失败需在**界面上可归因**，而非只给一行 `subtype=` |

## 2. 目标与非目标

### 2.1 目标

Phase 2 结束时，应成立：

1. **平台不再可能改写自身源码树**（S1）
2. **多个 agent 能真正并行工作**，且并行度来自 PM 的工作包拆解（P1–P4）
3. **`owns` 是真实强制边界**，越界写被拦截并留痕（S2）
4. **任务可取消**，僵尸任务不再堆积（O2）
5. **成本与时间有硬闸门**，单节点花费有上限（S6）
6. **节点级进度可实时观测**，不再依赖轮询与日志 mtime 拼接（O1）

### 2.2 非目标（明确不做）

- 不做 Web UI 的多用户/权限体系（仍是本机单用户运维台）
- 不做分布式部署（单机多进程；跨机调度不在本阶段）
- 不接入 Codex 引擎（`env.codexBin` 保留但不在本阶段启用）
- 不做角色的自由对话协商（Phase 1 的"零自由对话、只交换结构化 Artifact"是刻意的架构主张，维持不变）

## 3. P0 需求（必做）

> 每项格式：**问题（实证）/ 需求 / 验收标准 / 影响面 / 风险**

### P0-A 目标仓库隔离（安全前提，优先于一切）

**问题（S1）**：`repoPath = process.cwd()`。实测把平台指向自身源码树时，agent 改写了平台仓库并破坏 `tsc`。

**需求**
- A1 引入**显式的目标仓库**配置（例如 `AGENTFLOW_TARGET_REPO`），与平台自身仓库路径**分离**
- A2 启动时**校验**：目标仓库 ≠ 平台仓库（含符号链接解析后的比较）；若相同则**拒绝启动**并给出明确错误
- A3 目标仓库必须存在、是 git 仓库、且工作区干净（或有明确的豁免开关）
- A4 日志与事件库**不得**落在目标仓库内（避免污染目标仓库的 git 状态）
- A5 内核不再从 `process.cwd()` 推断任何仓库路径

**验收标准**
- 设 `AGENTFLOW_TARGET_REPO` 指向平台自身仓库时，服务**拒绝启动**，错误信息含两个路径与实际比较结果
- 端到端跑完后，平台仓库 `git status --short` **为空**（当前已能通过"在临时仓库里跑"绕过，但这是脚本纪律而非代码保证；A1–A5 要把它变成代码保证）
- 目标仓库内不出现 `logs/`、`data/`、`*.sqlite*`
- 新增单测覆盖：同路径 / 符号链接指向同一处 / 目标仓库非 git / 目标仓库不存在

**影响面**：`src/main.ts`、`src/config/env.ts`、`src/kernel/kernel.ts`（repoPath 来源）
**风险**：若目标仓库校验过严（例如要求工作区干净），会挡住"在已有脏工作区的项目上用平台"的正当场景 → 需判定为**警告**还是**拒绝**（见第 9 节待决策 Q1）

### P0-B 并发调度（用户核心诉求）

**问题（P1–P5）**：内核单节点 `await`；`globalConcurrency` 无消费者；`parallel`/`join` 零实现；`work_package_plan` schema 已定义但无产出者；worktree 有骨架不可达。

**需求**
- B1 **PM 工作包拆解接通**：`simple_dev` 增加产出 `work_package_plan` 的节点，payload 必须含每个工作包的 `id`、标题、`owns`（路径集合）、`interface_contract`、依赖关系
- B2 **`parallel` 节点类型**：一个父节点可扇出到 N 个子节点，同时运行，受 `globalConcurrency` 约束（该配置**必须真正被消费**）
- B3 **`join` 节点类型**：汇聚全部（或按策略）子节点，产出合并后的上下文
- B4 **worktree 池**：每个并行工作包独占一个 worktree（启用 `isolate`），结束后回收；池大小与并发度联动
- B5 **合并策略**：join 之后必须能合并各 worktree 的改动；**合并冲突必须显式失败并留下可诊断信息**（不得静默丢弃）
- B6 **调度公平与可观测**：当前并发度、等待队列、每个工作包的状态必须在状态投影中可见（新增 `workPackageId` 维度或等价结构）
- B7 **并发安全**：事件库写入、预算累计、投影在并发下必须无竞态（当前 `store.append` 为同步 `better-sqlite3`，需确认串行化假设仍成立）

**验收标准**
- 一个含 3 个可并行工作包的需求：事件流中出现 3 个节点的 `node.started` **时间区间重叠**（可从 `created_at` 判定），且重叠数 ≤ `globalConcurrency`
- `globalConcurrency=1` 时**退化为串行**（重叠数恒为 1）
- 每个并行节点写入的 `log_ref` **互不相同**，worktree 路径互不相同
- join 节点能看到全部上游 artifact，且合并结果正确（用两个分别改不同文件的包验证）
- 故意制造两包改同一文件 → **合并冲突被显式报告**，任务 `failed`，错误含冲突文件与双方来源
- 并发度、队列长度在 API 响应中可见（不得显示虚构值）

**影响面**：`src/kernel/kernel.ts`、新增 scheduler/合并模块、`src/kernel/state-machine.ts`、工作流 schema、`config/workflows/**`
**风险（必须正视）**
- 并发 + worktree 会显著放大**成本**（N 个 agent 同时烧钱）→ 必须与 P0-F 预算闸门**同批交付**，否则有失控风险
- 合并是新增的失败面；"冲突即失败"会让一些本可自动处理的场景失败 → 需明确策略（见 Q2）

### P0-C `owns` 路径级强制

**问题（S2）**：`owns` 只是 prompt 里一句话；实测越界写且任务正常完成；`artifact.invalidated` 无生产者。

**需求**
- C1 调度前做**占用检查**：同一时刻两个并发工作包的 `owns` 重叠 → 拒绝调度并报告（这是并行的前置条件）
- C2 节点结束后做**变更路径核对**：对比 worktree 内实际变更文件与 `owns`，越界则
  - 记 `artifact.invalidated` 事件（**必须真的产生该事件**，填补当前零生产者）
  - 按策略处理：警告 / 丢弃越界改动 / 使该产物失效（见 Q3）
- C3 文档口径同步：spec §7.2/§15 与实现一致（当前已标注为 Phase 1 缺口，Phase 2 需改为已强制）
- C4 越界必须在**界面上可见**（哪些文件越界、被如何处理）

**验收标准**
- 构造 `owns: ["src/**"]` 的角色写出 `README.md` → 产生 `artifact.invalidated`，事件含越界文件清单与角色
- 两个并发工作包 `owns` 重叠 → 调度被拒绝，错误指出重叠路径与两个包 id
- 越界在管理台可见（不只写在日志里）

**影响面**：`src/kernel/kernel.ts`、`src/kernel/context-assembler.ts`、`src/shared/events.ts`（新增事件类型）、投影器
**风险**：核对依赖 worktree 的 diff 计算，需定义"变更"的口径（是否含未跟踪文件、是否含删除）

### P0-D 任务生命周期：取消与停止

**问题（O2）**：库里存在永远 `active` 的僵尸任务；启停脚本的安全护栏因此每次都触发，失去判别力。

**需求**
- D1 `POST /api/tasks/:taskId/cancel`：取消运行中的任务
  - 先向在飞 runner 发终止信号（复用既有**进程组终止**机制），再落 `task.cancelled` 事件
  - **幂等**：对已终态任务返回明确错误，不产生副作用
  - 取消后 `budgetUsedUsd` 保留已花费金额（**不得清零**）
- D2 僵尸任务可被识别与清理：任务在 `active` 且无任何在飞 run、且最后事件时间超过阈值时，状态投影/接口应能标记为「疑似失联」
- D3 `task.cancelled` 进入状态机终态集合，工作流边不再推进
- D4 前端提供取消入口（二次确认，明示已花费金额）

**验收标准**
- 运行中任务取消后：进程组内无残留 `claude` 进程；事件流含 `task.cancelled`；最终 `status === 'cancelled'`
- 对 `completed`/`failed` 任务调 cancel → 4xx + 明确原因，**事件流无新增事件**
- 取消后 `budgetUsedUsd` > 0（与取消前一致）
- 清理僵尸任务后，启停脚本的护栏**不再**因它触发

**影响面**：`src/server/server.ts`、`src/kernel/kernel.ts`、`src/shared/events.ts`、投影器、`web/**`
**风险**：取消与并发调度交互复杂（多节点在飞时如何原子停止）→ 建议先只支持"取消整个任务"

### P0-E 节点级事件推送（替换轮询）

**问题（O1）**：`{type:'event'}` 通道无触发点；前端靠 2 秒轮询。

**需求**
- E1 内核提供**事件订阅接口**（回调/流），在 append 后通知订阅者
- E2 Server 层把节点级事件通过 WS 推 `{type:'event', event}`（**启用当前死代码通道**，或删除它并定义新契约——二选一，见 Q4）
- E3 前端改为事件驱动刷新，**保留轮询作为兜底**（WS 断连时不得失去更新能力）
- E4 WS 断线**自动重连**（修复 O4）

**验收标准**
- 节点状态变化在 WS 上被推送，前端刷新延迟 < 1 秒（对比轮询的 2 秒）
- 断开 WS 后前端仍能更新（轮询兜底生效），重连后恢复推送
- 推送不重复、不丢（用 `seq` 去重与断点续推验证）

**影响面**：`src/kernel/kernel.ts`、`src/server/server.ts`、`web/**`
**风险**：事件推送与并发调度（P0-B）叠加会放大事件量 → 需限流/批量策略

---

### P0-F 成本与时间闸门

**问题（S6、O5、C2）**：单节点无预算上限；`budgetCapUsd` 从不传；降级重试使上限实际 2×；usage 双写。

**需求**
- F1 **单节点预算上限**：内核必须传 `budgetCapUsd`；超限即终止该节点的 CLI 调用并记明确事件
- F2 **任务级预算上限**：`POST /api/tasks` 可带预算，累计超限则**停止推进后续节点**（不是静默继续）
- F3 **降级重试的上限必须计入总额**：文档与界面的"标称上限"需反映实际可能翻倍（或改为共享同一预算池）
- F4 收敛 usage 双写：`node.usage_recorded` 与 `budget.consumed` 二选一为主口径，另一个明确标注为派生；**成本闸门只认一个口径**（避免重复扣减或漏扣）
- F5 成本在界面上**按节点/按工作包**可见，超限显著提示

**验收标准**
- 传一个很小的单节点预算 → 节点被终止、事件含超限原因与已花金额、任务后续节点不推进
- 任务级超限 → 已完成的节点产物保留，未开始的节点不启动，状态为明确终态
- 并发 N 个节点时总花费不超过任务级上限（允许有界超出，但需在文档中量化说明）
- 界面上节点花费之和与任务累计一致（当前前端已做到精确对账，需保持）

**影响面**：`src/kernel/kernel.ts`、`src/config/env.ts`、`src/runner/**`、`web/**`
**风险**：硬闸门会打断本来能完成的任务 → 默认值应宽松，需显式开启

## 4. P1 需求（应当做）

| # | 需求 | 依据 | 验收标准（简） |
| --- | --- | --- | --- |
